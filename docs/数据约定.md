# 数据约定

## 邮箱边界

`Mailbox` 是唯一的外部输入边界：

- `list_uids()` 返回 `(UIDVALIDITY, [UID...])`；
- `fetch(uid)` 返回原始 MIME 字节；
- `acknowledge(uidvalidity, uid)` 只在当前世代存在该 UID 时才有效，失败不会设置标记；
- `reset(messages)` 模拟 UIDVALIDITY 重建，同一 UID 可以指向另一封信，旧标记全部清空；
- `redeliver(uid, raw)` 模拟同一 UID 被重新投递另一份字节；
- `fail_ack` 与 `ack_attempts` 用于演示/测试确认失败与重试次数。

`fixtures/source.json` 是合成邮件与邮箱元数据。样例中的机构、人员、地址和
标识均为虚构，没有真实邮箱密码，也不会联网。

## 邮件身份

一封邮件的业务身份由以下四项共同决定：

| 字段 | 含义 |
| --- | --- |
| 邮箱名 | 本地适配器默认 `local` |
| UIDVALIDITY | 邮箱世代；改变后同一 UID 是另一封信 |
| UID | 世代内的位置 |
| 原始字节 SHA-256 | 区分同 UID 的多次内容不同的投递 |

`Message-ID` 和主题只用于展示和人工核对，不参与唯一性判断。README 样例中
UID 11 与转发邮件内嵌的邮件共用同一个 `Message-ID`，但它们是两次独立投递。

世代重建不会删除旧世代的任何行；旧附件的来源查询仍返回原来的 UIDVALIDITY。
同一世代内同一 UID 出现新字节时，旧投递标记 `superseded_at` 并保留，新投递
单独入账；同名不同内容绝不会被当成覆盖。

## MIME 解析

`mime_parse.parse_message` 返回 `ParseResult`：

- `status`：`complete` 全部附件可存；`partial` 至少一项被隔离或结构可疑；
  `rejected` 整封无法处理（例如超过整封上限）。
- `attachments[i]`：`part_path`（从 1 开始的 MIME 部件路径，如 `2.1.2`
  表示转发邮件里的内层附件）、`original_filename`、原始
  `Content-Disposition`、`content_type`、`disposition`、`content_id`、
  `size`、`content` 以及隔离时的 `isolation_reason`。

隔离原因（`isolation_reason`）：

| 值 | 触发条件 |
| --- | --- |
| `decode_error` | base64 严格解码失败、内嵌邮件无法解析、编码与声明不符 |
| `unsupported_encoding` | 传输编码不在 7bit/8bit/binary/base64/quoted-printable 内 |
| `mime_defect` | 部件带结构性解码缺陷（如 base64 填充错误） |
| `too_large` | 单个附件超过 `max_attachment_bytes` |
| `total_size_limit` | 单封累计附件超过 `max_total_attachment_bytes` |
| `depth_exceeded` | 嵌套深度超过 `max_depth`，截断处不再继续解析 |
| `part_limit` | 单封部件数超过 `max_parts`，之后的部件不再遍历 |

资源上限默认值见 `Limits`：16 MiB/封、8 MiB/附件、32 MiB/封附件总量、
2000 个部件、12 层嵌套。base64 先按长度估算，超限时不解码；被截断的邮件
一律标记为 `partial`，不会声称整封已完整接收。

`message/rfc822` 带文件名时，转发邮件本身作为一条附件发布（内容为序列化后
的完整内嵌邮件），同时继续遍历内层部件；不带文件名时只作为容器，避免重复
发布。base64 编码的 `message/rfc822` 无法可靠解析，进入隔离区。
空附件（内容为 0 字节）是合法附件，会正常存储。

`reader.preview` 保留原有行为（附件名与类型），`reader.assess` 额外给出部件
路径、状态与隔离原因。

## 存储与账本

`state/` 下有两类数据：

- `content/<sha256>`：附件内容，文件名只由内容摘要生成。发件人提供的文件名
  只作为账本元数据，不参与磁盘路径；路径分隔符、绝对路径和 `..` 都不会
  逃出内容目录。
- `ledger.sqlite3`：接收账本。

账本表：

| 表 | 用途 |
| --- | --- |
| `generation` | 每个 `(邮箱, UIDVALIDITY)` 一行 |
| `delivery` | 每次投递一行，含原始字节指纹、解析/接收状态、取代时间 |
| `attachment` | 每个 MIME 部件一行，含部件路径、原始文件名、内容摘要、隔离原因 |
| `content` | 内容摘要与大小，多个附件可共用 |
| `receipt` | 远端确认状态：`pending`/`confirmed`/`failed`/`blocked`/`stale` |
| `ledger_event` | 追加式事件：入账、发布、隔离、确认、补写、失效等 |

`delivery.receive_status` 为 `received`（全部附件已存且邮件结构正常）、
`partial`（有隔离项或结构缺陷）、`rejected`（整封无法处理）。
`receipt.status` 只有 `received` 的投递才可能是 `pending`；`partial`/`rejected`
一开始就是 `blocked`，不会更新远端处理标记。

相同内容重复出现时共用 `content` 与磁盘文件，但 `attachment` 仍按每次投递
分别记录。

## 接收与恢复顺序

1. 解析邮件并写入内容存储（内容存储只做新增，摘要文件名天然幂等）。
2. 在单个 SQLite 事务中提交投递、附件和 receipt。
3. 事务提交后才调用 `acknowledge`；成功则 receipt 记为 `confirmed`。
4. 任一步失败或进程崩溃，下一轮 `collect()` 会：
   - 对 `pending`/`failed` 且内容完整的投递重试确认；
   - 内容文件缺失时按账本里的部件路径从邮箱重新读取、校验邮件指纹后补写，
     不会重新发布附件行；
   - 远端标记已存在但本地仍是 `pending`/`failed` 时补记确认，不重复调用；
   - 旧世代的未确认凭据标记为 `stale`，不再向旧世代写标记。

因为内容、账本和远端标记没有共同事务，可能出现“附件已存但未确认”或
“远端已标记但账本未记”；这两种状态都是可恢复且不会造成重复发布的。

## 查询接口

`Collector.delivery_source(id)`、`attachment_source(id)`、`content_source(hash)`、
`isolated()`、`status()` 分别给出投递、附件、内容摘要、隔离清单与账本计数。
命令行：

```bash
python3 app.py                    # 原有预览
python3 app.py --assess           # 预览部件路径、状态、隔离原因
python3 app.py --collect          # 批量采集到 state/
python3 app.py --collect --fail-ack
python3 app.py --collect --fault after_blob_write   # 演示落盘后崩溃
python3 app.py --attachments      # 列附件及来源投递
python3 app.py --source 2         # 查附件 2 的来源
python3 app.py --quarantine       # 列隔离附件及原因
python3 app.py --ledger           # 账本计数
python3 app.py --demo             # 临时目录内演示投递重投、UID 重置、确认失败
```

`--demo` 不写 `state/`，结束后删除临时目录。
